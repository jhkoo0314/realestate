# 부동산 매물관리 도구 구현 작업표

> 작업 방식: 먼저 작동하는 뼈대를 만들고, 매 단계마다 실제 브라우저 화면을 보면서 수정한다.
>
> 기준 문서: `docs/` 폴더의 PRD, 데이터 항목 정의서, 화면 명세, 업무 흐름서, 테스트·운영 문서

## 0. 이 문서 사용법

- 한 번에 완성하려 하지 않는다. 아래 **단계 순서대로** 만든다.
- 각 작업을 마치면 브라우저에서 직접 확인한 뒤 체크박스를 표시한다.
- 화면을 보고 불편한 점이 생기면 바로 코드를 고치기보다, 먼저 이 문서의 `결정 기록`에 적는다.
- 기능을 바꿀 때는 관련된 `docs/` 문서와 테스트 항목도 함께 확인한다.
- 1차 버전의 목표는 “화려한 서비스”가 아니라 **매물을 빠르고 안전하게 등록·확인하는 내부 도구**다.

### 코드 파일과 폴더를 나누는 원칙

- `app.py`는 프로젝트 최상위 폴더에 두는 프로그램의 **입구**다. 상단 메뉴, 공통 화면 모양, 화면 전환만 관리한다.
- 사용자에게 보이는 화면은 `ui/` 폴더에서 관리한다.
- 신규 등록·재등록·수정의 입력 검사와 업무 규칙은 `services/` 폴더에서 관리한다.
- 데이터 파일을 읽고 저장하는 코드는 `storage/` 폴더에서 관리한다.
- 새 기능이 생길 때는 역할에 맞는 기존 폴더에 파일을 추가한다. 루트 폴더에 기능 파일을 계속 쌓지 않는다.
- 공통 선택값, 입력 검사, 화면 문구처럼 여러 기능이 함께 쓰는 내용도 필요해질 때 역할별 폴더에 공통 파일로 관리한다.
- 처음부터 불필요하게 많은 파일을 만들지는 않는다. 기능이 실제로 생기는 단계에 맞춰 한 파일씩 추가한다.

현재 구조:

```text
C:\realestate\
├─ app.py                  # 실행과 메뉴 전환
├─ ui\                     # 사용자 화면
├─ services\               # 등록·수정 규칙
├─ storage\                # 데이터 저장과 실제 데이터 파일
└─ docs\                   # 기획·작업 문서
```

## 1. 완성 모습

사무실 직원이 브라우저에서 다음 3개 화면을 사용한다.

1. **매물 현황 리스트**: 현재 매물을 조회·필터하고 확인 업무를 찾으며, 조회 결과를 엑셀로 내보낸다.
2. **매물 등록·수정**: 새 건물·호실·매물을 등록하거나 기존 호실의 최신 정보를 수정·종료한다.
3. **건물·호실 관리**: 건물 공통정보, 호실 고정정보, 과거 매물 이력을 확인한다.

핵심 안전장치:

- 동일 건물·호실의 중복 등록 방지
- 기존 호실 최신 정보 수정 시 계약·상담 연결 유지
- 비밀번호·내부 메모의 기본 목록 노출 방지
- 저장 오류 시 입력한 내용 유지
- 원본 데이터와 백업 파일 분리

## 2. 1차 버전에서 만들 범위

### 반드시 만든다

- 건물, 호실, 매물 회차 저장
- 건물명·지번·호수 검색
- 신규 등록, 기존 건물의 새 호실 등록, 기존 호실 최신 정보 수정
- 현재 매물 조건 수정 및 매물 종료
- 오늘의 확인 업무(재확인·사진·현장·입주일·광고 준비)
- 목록 검색·필터·상세 보기
- 일반 매물 목록 엑셀 내보내기
- SQLite 데이터 저장과 백업
- 매물 회차에 연결한 단기·일반 계약 기간과 상태 관리
- 매물 회차에 연결한 간단한 상담 이력과 다음 연락 관리

### 이번에는 만들지 않는다

- 기존 `구재현` 시트 자동 가져오기
- 방문 예약, 자동 문자 발송, 주민번호 등 민감 개인정보, 계약금·잔금의 납부·결제 관리
- 외부 인터넷 공개, 로그인, 권한별 사용자 관리
- 사진 파일 업로드·사진 위치·사진 폴더 경로·링크 관리
- 여러 사람이 같은 매물을 동시에 수정하는 기능

## 단계 3 — 신규 등록 화면 만들기

목표: 새 건물, 새 호실, 첫 매물을 한 번에 안전하게 등록한다.

### 이 단계에서 만들 파일 역할

- [x] `app.py`: 등록 화면을 선택해 보여 주기만 한다.
- [x] `ui/listing_form.py`: 신규 등록 화면과 저장 전 확인 화면을 담당한다.
- [x] `services/listing_service.py`: 입력값 검사와 건물·호실·매물 저장 순서를 담당한다.
- [x] `storage/database.py`: `listing_service.py`가 요청한 저장·조회만 처리한다.

등록 화면이 커져도 `app.py`에 입력칸과 저장 규칙을 직접 추가하지 않는다.

### 기본 입력칸

- [x] 건물명(필수), 지번(필수)
- [x] 호수(필수), 룸 형태, 층, 방향
- [x] 매물 접수일(기본값 오늘, 실제 접수일로 수정 가능), 매물 상태(필수)
- [x] 보증금·월세(필수, 만원 단위 숫자)
- [x] 관리비, 입주 가능 유형, 입주 가능일
- [x] 사진 보유 여부, 이번 매물 메모
- [x] 호실 옵션: 냉장고, 세탁기, 에어컨, TV, 가스렌지, 인덕션, 옷장, 신발장 체크와 기타 옵션 메모

### 입력 검사

- [x] 건물명 또는 지번이 비면 저장하지 않는다.
- [x] 호수가 비면 저장하지 않는다.
- [x] 보증금·월세에는 숫자 입력칸을 사용하고, 비어 있거나 0이면 이유를 알려 준다.
- [x] 입주 가능 유형이 `날짜 지정`이면 날짜 입력을 요구한다.
- [x] 오류가 나도 이미 입력한 내용은 지우지 않는다.
- [x] 저장 전 `건물명 · 지번 · 호수 · 보증금/월세` 요약을 보여 준다.
- [x] 건물·호실·첫 매물은 모두 성공할 때만 한꺼번에 저장한다. 중간에 하나라도 실패하면 일부만 저장되면 안 된다.

### 화면 확인

- [x] 테스트용 `대성빌 / 북수리 1026 / 302호 / 500/45`를 별도 테스트 데이터 파일에 저장한다.
- [x] 저장한 건물·호실·매물 1건과 상세값을 다시 읽어 확인한다.
- [x] 필수값 누락과 날짜 지정 후 날짜 누락을 자동 시험한다.
- [ ] 실제 브라우저에서 신규 등록 화면의 입력 흐름과 저장 결과를 확인한다.

## 단계 4 — 검색·중복 방지 만들기

목표: 같은 건물이나 같은 호실을 잘못 여러 번 만들지 않는다.

- [x] 건물명 또는 지번으로 기존 건물을 찾는다.
- [x] `건물명 + 지번`이 같으면 기존 건물을 먼저 보여 준다.
- [x] 건물명은 같아도 지번이 다르면 자동으로 합치지 않는다.
- [x] 같은 건물에서 같은 호수를 새로 등록하지 못하게 한다.
- [x] `302`와 `302호`를 같은 호실로 처리한다.
- [x] 기존 건물을 선택하면 주소·공동현관·주차 같은 건물 정보는 다시 입력하지 않는다.

### 화면 확인

- [ ] 대성빌을 다시 검색했을 때 기존 건물이 우선 보인다.
- [ ] 대성빌에 302호를 다시 만들려고 하면 막힌다.
- [ ] 대성빌에 201호를 새로 등록할 수 있다.

## 단계 5 — 기존 호실 최신 정보 수정

목표: 기존 호실을 선택해 새로 확인한 조건만 입력하고 최신 매물 정보를 바로 갱신한다.

- [x] 건물과 호실을 선택할 수 있다.
- [x] 호실의 고정정보(구조·방향·옵션·방문 방법)를 자동으로 불러온다.
- [x] 기존 최신 조건을 불러와 필요한 값만 수정할 수 있다.
- [x] `최신 정보 저장` 버튼으로 같은 매물 기록을 갱신한다.
- [x] 저장 시 연결된 계약·상담 기록을 유지한다.
- [x] 기존 호실을 선택하면 최신 정보 입력칸을 바로 연다.
- [x] 실제로 다시 확인하지 않은 비밀번호·옵션의 마지막 확인일을 자동으로 오늘 날짜로 바꾸지 않는다.

### 화면 확인

- [ ] 대성빌 302호를 선택해 `500/47, 공실, 즉시입주`로 최신 정보를 저장한다.
- [ ] 연결된 계약·상담 기록이 그대로 남아 있는지 확인한다.

## 단계 6 — 현재 매물 수정과 종료 만들기

목표: 현재 매물의 변경과 매물 종료를 헷갈리지 않게 한다.

- [x] `현재 매물 수정`은 같은 매물 회차의 가격·상태·입주일·메모만 수정한다.
- [x] 여러 항목을 바꿔도 저장 버튼을 누를 때 한 번에 반영한다.
- [x] 사진 보유 여부를 바꾸면 사진 촬영·확인 필요 업무가 자동으로 갱신된다.
- [x] 종료 시 종료일과 종료 사유를 기록한다.
- [x] 계약 여부를 실제로 확인하기 전에는 자동으로 `계약 완료`로 바꾸지 않는다.
- [x] 잘못 등록한 매물은 `정보 오류`로 종료하거나, 확인 후 완전 삭제할 수 있다. 완전 삭제 시 연결된 계약·상담 기록도 함께 삭제한다.
- [x] 건물은 비활성화 방식으로 유지한다. 잘못 만든 호실은 삭제 대상 매물·계약·상담 건수를 확인한 뒤 완전 삭제할 수 있게 한다.

### 화면 확인

- [ ] 월세만 수정해도 새 매물 회차가 생기지 않는다.
- [ ] 계약 완료 처리한 매물은 현재 목록에서는 사라지고 이력에는 남는다.

## 단계 7 — 매물 현황 리스트 화면 만들기

목표: 현재 매물을 조회·필터하고, 필요한 확인 업무를 찾는다.

### 상단 요약

- [x] 오늘 새 접수
- [x] 퇴실 예정
- [x] 재확인 필요
- [x] 사진 촬영 필요
- [x] 공실

### 검색과 필터

- [x] 건물명, 지번, 호수 통합 검색
- [x] 매물 접수일 기간 필터: 시작일과 종료일을 선택해 그 기간에 접수된 매물만 찾기
- [x] 보증금·월세 범위 필터: 각각 최소·최대 금액(만원)을 입력해 조건에 맞는 매물만 찾기
- [x] 매물 상태 필터

## 3-1. 단계별 상세 구현계획과 테스트

### 공통 진행 원칙

각 단계는 아래 순서로 진행한다.

1. **작은 기능 하나를 만든다.** 예: 메뉴 하나, 저장 버튼 하나처럼 범위를 작게 잡는다.
2. **개발자가 확인한다.** 코드가 오류 없이 실행되고, 기본적인 자동 확인을 통과하는지 본다.
3. **브라우저에서 직접 확인한다.** 실제 사무실 사용자가 누르는 순서대로 눌러 본다.
4. **문제 기록 후 수정한다.** 오류 화면, 어떤 버튼을 눌렀는지, 기대한 결과를 `결정·수정 기록`에 남긴다.
5. **다시 확인한다.** 수정한 부분뿐 아니라 관련된 기존 기능도 한 번 더 확인한다.

테스트 결과 표기:

- **PASS**: 기대한 대로 동작함
- **FAIL**: 다르게 동작하거나 업무를 할 수 없음
- **BLOCKED**: 앞선 오류나 PC 환경 문제로 시험할 수 없음

### 단계 1 상세 — 실행 가능한 빈 화면

#### 구현 순서

1. 프로그램 시작 파일(`app.py`)을 만든다.
2. 화면 이름, 사무실 내부용 안내문, 기본 넓이를 설정한다.
3. 메뉴 상태를 한 곳에서 관리해 메뉴를 눌러도 화면 선택이 흔들리지 않게 한다.
4. 각 메뉴 화면은 우선 제목·설명·빈 상태만 보여 주는 함수로 나눈다. 이렇게 하면 다음 단계에서 한 화면을 고쳐도 다른 화면에 영향을 덜 준다.
5. 데이터가 없을 때 등록 화면으로 이동하는 버튼을 연결한다.

#### 테스트 및 합격 기준

| S1-02 | 세 메뉴를 차례로 누른다. | 선택한 메뉴의 제목과 내용이 각각 보인다. | 화면 명세 2장 |
| S1-03 | 데이터가 없는 상태에서 첫 화면을 본다. | 빈 표가 아니라 첫 매물 등록 안내와 버튼이 보인다. | TC-043 |
| S1-04 | 등록 안내 버튼을 누른다. | `매물 등록·수정` 화면으로 이동한다. | 화면 명세 7.4 |

**단계 완료 조건:** S1-01~04가 모두 PASS이고, 화면을 처음 보는 사람이 메뉴와 등록 버튼을 찾을 수 있다.

#### 구현 순서

1. 데이터 파일의 위치를 설정 파일 또는 한 곳의 상수로 정한다. 코드 여러 곳에 경로를 적지 않는다.
2. 건물·호실·매물 회차용 표를 만든다. 각 기록에는 내부 번호, 만든 시각, 수정 시각을 둔다.
3. 건물과 호실, 호실과 매물 회차의 연결 규칙을 만든다.
4. 데이터 파일이 없거나 경로가 틀렸을 때의 안내를 만든다.
5. 저장, 한 건 조회, 목록 조회 기능을 화면과 분리된 코드로 만든다. 화면 디자인을 고쳐도 저장 규칙이 깨지지 않게 하기 위함이다.

### 단계 6 상세 — 현재 매물 수정과 종료

1. 현재 매물의 상세 화면에 `현재 매물 수정`을 둔다.

### 단계 7 상세 — 매물 현황 리스트

#### 구현 순서

1. 현재 활성 매물만 기본 목록에 가져온다.

3. 검색어와 각 필터를 조합해 하나의 목록 결과를 만든다.

## 추가 운영 계획 — 개발 완료 후 메인 PC 이전 및 2인 전용 접속

목표: 개발 PC에서 기능·저장·백업 확인을 모두 끝낸 뒤에만 프로젝트 전체를 사무실 메인 PC로 옮기고, 두 명만 안전하게 접속한다. 개발 중에는 이전하거나 운영 데이터를 분산하지 않는다.

### 운영 방식 결정

- [x] 초기 운영은 **메인 PC + 현재 SQLite 데이터 파일 + Tailscale** 방식으로 한다.
- [ ] Streamlit Community Cloud에는 운영 데이터 파일을 올리지 않는다. 로컬 파일 저장은 영구 보관이 보장되지 않고, 연락처·비밀번호가 포함된 데이터 파일을 GitHub에 보관하면 안 된다.
- [ ] 메인 PC는 사무실의 항상 켜진 PC 또는 전용 미니 PC로 정한다.
- [ ] 두 사용자만 각자의 Tailscale 계정으로 메인 PC에 접속하도록 허용한다.
- [ ] 외부에서도 접속할 때는 일반 인터넷 주소를 공개하지 않고, Tailscale 개인 네트워크 안에서만 접속한다.
- [ ] 매물 데이터 파일은 **메인 PC의 `storage\real_estate.db` 한 곳에서만** 사용한다. 사용자 PC에는 데이터 파일을 복사하거나 직접 열지 않는다.
- [ ] 메인 PC에서 프로그램은 본인 PC에서만 열리도록 실행하고, Tailscale Serve를 통해서만 두 사용자 PC에 연결한다. 일반 인터넷에 공개하는 Tailscale Funnel은 사용하지 않는다.

### 개발 완료 후 이전 순서

1. 개발 PC에서 신규 등록·최신 정보 수정·계약·상담·엑셀·백업 확인을 끝낸다.
2. 프로그램을 완전히 종료한 뒤, 프로젝트 폴더 전체를 메인 PC의 고정 위치(예: `C:\realestate`)로 복사한다.
3. 반드시 `storage\real_estate.db`와 백업 폴더를 함께 복사한다. 데이터 파일만 따로 복사하거나 GitHub에 올리지 않는다.
4. 메인 PC에 Python 3.12 환경과 필요한 패키지를 설치하고, `streamlit run app.py`로 먼저 메인 PC에서 실행 확인한다.
5. 메인 PC와 두 사용자 기기에 Tailscale을 설치하고, 두 사용자 계정만 메인 PC 접속 권한을 준다.
6. 메인 PC에서 Tailscale Serve를 설정해, 메인 PC에서만 실행 중인 프로그램을 Tailscale 내부 주소로 연결한다. 인터넷에 공개하는 기능(Funnel)은 켜지 않는다.
7. 두 사용자 PC에서 안내받은 Tailscale 내부 주소를 브라우저로 열어 같은 매물 목록을 보는지, 한쪽에서 저장한 내용이 다른 쪽에 보이는지 확인한다.
8. 이전 완료 후 개발 PC의 데이터 파일은 즉시 삭제하지 않고, 읽기 전용 백업본으로 보관한다.

### 이전 완료 기준

- [ ] 메인 PC에서 기존 건물·호실·매물·계약·상담 기록이 모두 보인다.
- [ ] 두 사용자만 접속할 수 있고, 제3자가 일반 인터넷 주소로 접속할 수 없다.
- [ ] 한 사용자의 저장·수정 결과를 다른 사용자가 새로 조회해 확인할 수 있다.
- [ ] 메인 PC 재시작 후에도 앱과 데이터가 정상 실행된다.
- [ ] 이전 전 데이터 파일과 이전 후 데이터 파일의 건물·호실·매물·계약·상담 건수가 같다.
- [ ] 백업 파일을 별도 위치에서 열어 조회하는 복구 확인을 마쳤다.
- [ ] 사용자 PC에 `real_estate.db` 파일이 없고, 모든 저장은 메인 PC 데이터 파일 한 곳에 반영된다.

### 향후 전환 검토 기준

- 메인 PC를 계속 켜둘 수 없거나, 사무실 밖에서도 PC 상태와 무관하게 접속해야 하면 Supabase 같은 외부 데이터베이스 전환을 별도 단계로 검토한다.
- 외부 데이터베이스 전환 시에는 두 사용자 로그인, 접근 권한 제한, 비밀번호·연락처 보호 방식, 기존 SQLite 데이터 이전과 복구 시험을 먼저 설계한다.

### 상담 진행관리 1차 (2026-08-10)

- 후속 상담 종료 사유에 `계약완료`를 추가했다. 등록·수정·필터·기존 상담 종료 처리에서 동일하게 선택·저장한다.
- 후속 상담 이력 수정에서 결과 단계가 `계약 완료`인 경우에도 선택한 종료 사유를 저장·표시한다. `종료`일 때만 종료 사유 입력을 필수로 검사한다.
- 기존 상담 기록은 일괄 변환하지 않고, 새 상담은 진행 단계를 메뉴에서 직접 선택해 후속 상담 이력과 함께 사용한다. 기본 선택값은 `신규 문의`다.
- 후속 전화·문자·방문 기록은 기존 첫 상담 내용을 덮어쓰지 않고 별도 이력으로 누적한다. 종료 시 종료 사유를 받고 다음 연락일을 자동 취소한다.
- 후속 상담 이력은 선택한 한 건만 수정하거나 명시적 확인 뒤 삭제할 수 있으며, 수정·삭제 뒤에는 남아 있는 가장 최근 이력으로 상담 요약을 다시 맞춘다.

- 후속 상담 등록·수정에서는 결과 단계와 관계없이 방문 결과 메뉴를 함께 표시하며, 방문 상담이 아니면 `미입력`으로 둔다.
- 후속 상담 등록·수정에서는 종료 사유 메뉴를 항상 선택할 수 있게 표시하고, 결과 단계를 `종료`로 저장할 때만 필수로 검사한다.

### 계약 중개 방식 분리 (2026-08-10)

- `공동중개`는 계약 유형이 아니라 중개 방식으로 분리한다. 계약 유형은 일반 계약·단기계약·확인 필요를 유지한다.
- 중개 방식은 단독중개·공동중개·확인 필요를 선택하며, 등록·수정·조회·엑셀에 반영한다.

### 상담·매물 입력 및 오늘 할 일 화면 보완 (2026-08-10)

- 상담 조회 결과에 건물명·지번주소·호실을 함께 표시한다. 기존 상담은 별도 종료 처리로 기존 메모를 보존하고 종료 사유·다음 연락일만 갱신한다.
- 룸 형태의 신규 등록·수정·현황 필터 선택값에서 `분리형 원룸`을 제거하며, 기존 저장값은 목록·이력에서 유지한다.
- 완료한 오늘·지연 업무는 기본으로 숨기고 `완료 업무 보기`에서만 다시 표시한다. 현재 표시 업무만 엑셀로 내보내고, 날짜 업무가 없는 업무 구분 표는 숨긴다.
