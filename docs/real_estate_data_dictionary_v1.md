# 부동산 매물관리 도구 데이터 항목 정의서 v1.1

> 적용 범위: 원룸·투룸 중심의 사무실 내부용 매물장 1차 버전
>
> 기준: 기존 `구재현` 시트는 이관하지 않는다. 이 문서는 신규 화면 입력, SQLite 저장, 엑셀 내보내기의 공통 기준이다.

## 1. 문서 목적

이 문서는 같은 정보를 어디에 저장할지, 언제 새 기록을 만들지, 어떤 값만 선택할 수 있는지를 정의한다.

이 기준 없이 개발하면 다음 오류가 생길 수 있다.

- 보증금·월세를 호실 정보에 저장해 과거 가격이 사라짐
- 공동현관 비밀번호를 매물마다 반복 저장해 변경 여부를 알 수 없음
- 같은 건물을 표기만 다르게 중복 등록함
- `입주 가능`, `즉시`, `8월 이후` 같은 자유문구가 섞여 필터가 되지 않음

## 2. 핵심 원칙

1. **건물 → 호실 → 매물 회차** 순서로 저장한다.
2. 같은 호실이 다시 매물로 나오면 기존 행을 수정하지 않고 **새 매물 회차**를 만든다.
3. 모르는 정보는 억지로 입력하지 않는다. 빈값 또는 `확인 필요`를 사용한다.
4. 내부 비밀번호와 내부 메모는 광고·공유용 데이터와 분리한다.
5. 금액은 데이터베이스에 숫자로 저장하고, 화면에서만 `만원`으로 표시한다.
6. 자유메모는 보조수단이다. 상태·날짜·금액처럼 검색해야 할 값은 별도 항목으로 저장한다.

## 3. 데이터 구조 요약

```text
건물 1개
 └─ 호실 여러 개
     └─ 매물 회차 여러 개
         └─ 향후: 상담·방문·계약 기록 여러 개
```

| 구분 | 저장 목적 | 예시 |
|---|---|---|
| 건물 | 여러 호실에 공통인 정보 | 대성빌, 북수리 1026, 공동현관 비밀번호 |
| 호실 | 같은 호실에서 대체로 유지되는 정보 | 302호, 원룸, 붙박이장, 방문 방법 |
| 매물 회차 | 이번에만 적용되는 조건과 상태 | 500/45, 8월 20일 입주 가능, 퇴실 예정 |
| 확인 업무 | 당장 처리할 행동 | 사진 촬영 필요, 비밀번호 재확인 필요 |

## 4. 공통 시스템 항목

아래 항목은 모든 주요 데이터에 자동으로 기록한다. 사용자가 직접 입력하지 않는다.

| 화면명 | DB 항목명 | 형식 | 입력 | 설명 |
|---|---|---|---|---|
| 고유번호 | `id` | 정수, 자동 증가 | 자동 | 각 기록을 구분하는 내부 번호 |
| 생성일시 | `created_at` | 날짜·시간 | 자동 | 최초 저장 시각 |
| 수정일시 | `updated_at` | 날짜·시간 | 자동 | 마지막 수정 시각 |
| 활성 여부 | `is_active` | 예/아니오 | 자동·관리자 수정 | 더 이상 사용하지 않는 건물·호실을 숨길 때 사용 |

`id`는 사용자가 볼 필요가 없지만, 건물명이나 호수가 바뀌어도 기록을 정확히 연결하기 위해 반드시 필요하다.

### 중복 등록 규칙

- `지번 + 건물명`이 같으면 기존 건물 후보로 먼저 보여준다.
- 건물명만 같고 지번이 다르면 자동으로 같은 건물로 합치지 않는다.
- 건물명이 없거나 불확실하면 `건물명 미입력`으로 저장한다. 같은 지번의 같은 표기로는 중복 등록하지 않으며, 임의 합침은 금지한다.

- **기본등록:** 건물명·지번만 있는 초기 상태

# 6. 호실 항목 정의

## 6.1 호실 식별·구조 정보

| 화면명 | DB 항목명 | 형식 | 필수 | 입력 방식 | 설명 / 규칙 |
|---|---|---|---:|---|---|
| 건물 번호 | `building_id` | 정수 | 자동 | 자동 연결 | 선택한 건물의 고유번호. 화면에서는 보통 표시하지 않는다. |
| 호수 | `unit_number` | 짧은 텍스트 | 예 | 직접 입력 | 예: 302, 302호. 저장 시 `호` 표기를 제거하고 일관되게 관리한다. |
| 층 | `floor_number` | 정수 | 아니오 | 자동 제안·수정 | 302호면 3층을 제안할 수 있으나, 사용자가 수정 가능해야 한다. |
| 룸 형태 | `room_type` | 선택 | 권장 | 선택 | 원룸 / 투룸 / 투베이 / 쓰리룸 / 쓰리베이 / 주인세대 / 기타 / 확인 필요. `분리형 원룸`은 새 선택값에서 제거하며, 기존 저장값은 목록·이력에서 유지한다. |
| 분리형 여부 | `is_separated` | 선택 | 아니오 | 선택 | 예 / 아니오 / 확인 필요 |
| 방향 | `direction` | 선택 | 아니오 | 선택 | 동 / 서 / 남 / 북 / 남동 / 남서 / 북동 / 북서 / 확인 필요 |
| 면적 상태 | `area_status` | 선택 | 아니오 | 선택 | 면적 확인 / 면적 미확인 |
| 전용면적 | `exclusive_area_m2` | 숫자 | 조건부 | 직접 입력 | `면적 확인`일 때만 입력. 다가구 등 정확하지 않으면 비워둔다. |

### 호실 중복 규칙

- 같은 건물 안에서 `호수`는 하나만 등록한다.
- 302호와 302는 같은 호실로 처리하도록 입력 시 정규화한다.
- `101-1`, `A동 201` 등 예외 표기는 원문을 유지하되, 같은 표기가 중복 등록되지 않게 확인한다.
- 호실 번호를 오입력했을 때는 호실 번호 정정으로 기존 호실 기록의 번호만 바꾼다. 연결된 매물·계약·상담 이력은 유지하며, 기존 호실을 삭제하고 새로 등록하지 않는다.

### 옵션 저장 규칙

- 화면에서는 체크박스로 입력한다.

- 특별한 옵션만 `기타 옵션 메모`에 직접 입력한다.
- 이번 매물에만 옵션이 달라진 경우에는 호실 고정정보를 바로 바꾸지 않고, 매물 회차의 `옵션 변경 메모`에 우선 기록한다.

# 7. 매물 회차 항목 정의

매물 회차는 “이번에 나온 매물 한 번”을 뜻한다. 동일 호실이 재등록될 때마다 새 행을 만든다.

## 7.1 접수·상태 정보

| 화면명 | DB 항목명 | 형식 | 필수 | 입력 방식 | 설명 / 규칙 |
|---|---|---|---:|---|---|
| 호실 번호 | `unit_id` | 정수 | 자동 | 자동 연결 | 선택한 호실의 고유번호 |
| 접수일 | `received_date` | 날짜 | 자동 | 자동·수정 | 기본값은 저장일. 필요한 경우 사용자가 실제 접수일로 수정 가능 |
| 매물 상태 | `listing_status` | 선택 | 예 | 선택 | 아래 상태값만 사용 |
| 매물 보유처 | `listing_holder` | 선택·짧은 텍스트 | 신규 등록 예 | 선택·수정 | 크린주택관리 / 삼성주택관리 / 한빛주택관리 / 국제주택관리 / 개인매물 / 직접입력. 해당 매물 회차를 실제로 보유·관리하는 곳이며, 기존 빈값은 자동으로 넣지 않는다. |
| 종료일 | `closed_date` | 날짜 | 아니오 | 자동·수정 | 계약 완료·종료 등으로 바꿀 때 기록 가능 |
| 종료 사유 | `close_reason` | 선택 | 아니오 | 선택 | 계약 완료 / 타 부동산 계약 / 임대인 보류 / 정보 오류 / 광고 중단 / 기타 |

| 퇴실 예정 | 아직 입주자가 있으나 퇴실 예정 | 예 |
| 공실 | 현재 비어 있음 | 예 |
| 광고 가능 | 광고 조건 확인이 끝남 | 예 |
| 계약 진행 중 | 계약 가능성이 있으나 확정 전 | 예 |
| 계약 완료 | 계약이 확정됨 | 아니오, 이력에서 확인 |
| 보류 | 임대인·현장 사정으로 잠시 중단 | 필요 시 |
| 종료 | 더 이상 관리하지 않는 회차 | 아니오, 이력에서 확인 |

`계약 완료`는 매물이 목록에서 사라졌다는 이유만으로 자동 변경하지 않는다. 실제 확인 후에만 변경한다.

### 금액 입력 규칙

- 화면 라벨에 항상 `(만원)`을 표시한다.
- `500/45`, `500만원`, `45만` 같은 입력을 자유문구로 저장하지 않는다.
- 보증금·월세는 각각 비워 둘 수 있다. 전세는 월세를 비워 두며, 가격 자체가 미확정이면 0으로 저장하지 않고 `가격 확인 필요` 상태와 메모로 처리한다.
- 매물 현황 리스트에서는 보증금·월세를 각각 최소·최대 금액(만원)으로 필터할 수 있다. 해당 금액이 비어 있는 매물은 그 금액 범위를 선택했을 때 조회하지 않으며, 최대값은 최소값보다 작을 수 없다.

# 9. 초기 데이터 등록 원칙

- 기존 `구재현` 시트는 SQLite로 이전하지 않는다.
- 새 도구 사용 시점부터 현재 운영할 매물만 직접 등록한다.

- 실제로 매물이 나온 건물·호실만 등록한다.
- 과거 엑셀은 필요할 때 사람이 확인하는 참고자료로만 유지한다.
- 과거 엑셀을 자동으로 읽거나 변환하는 기능은 1차 범위에 포함하지 않는다.

# 11. 계약 기록

계약 기록은 건물이나 호실이 아니라, **그때의 매물 회차**에 연결한다. 같은 호실에 계약이 반복돼도 각각 별도 계약 기록으로 남긴다.

```text
매물 회차 1개
└─ 계약 기록 여러 개
```

| 화면명 | DB 항목명 | 형식 | 필수 | 설명 / 규칙 |
|---|---|---|---:|---|
| 계약 번호 | `id` | 정수 | 자동 | 계약 기록의 내부 번호. 화면·엑셀에는 `C-000001` 형식으로 표시 |
| 매물 회차 번호 | `listing_id` | 정수 | 자동 | 어느 시점의 매물에 연결됐는지 나타냄. 화면·엑셀에는 `M-000001` 형식으로 표시 |
| 출처 상담 번호 | `source_consultation_id` | 정수 | 아니오 | 계약으로 이어진 상담 기록. 상담 당시 매물 연결은 바꾸지 않으며, 화면에는 `S-000001` 형식으로 표시 |
| 계약 유형 | `contract_type` | 선택 | 예 | 일반 계약 / 단기계약 / 확인 필요 |

#### 계약 단계 이력 (`contract_activities`)

계약 한 건에는 실제 처리 순서에 따라 여러 단계 이력을 누적한다. 기존 계약의 날짜·금액·메모는 이력 저장으로 덮어쓰지 않는다.

| 화면명 | DB 항목명 | 형식 | 필수 | 설명 / 규칙 |
|---|---|---|---:|---|
| 이력 번호 | `id` | 정수 | 자동 | 계약 단계 이력의 내부 번호 |
| 계약 번호 | `contract_id` | 정수 | 예 | 연결된 계약. 계약 삭제 시 이력도 함께 삭제 |
| 처리일 | `activity_date` | 날짜 | 예 | 해당 단계를 실제로 처리·확인한 날 |
| 계약 단계 | `activity_stage` | 선택 | 예 | 새 입력: 가계약 / 정식계약 / 잔금 예정 / 계약 완료 / 해지. 과거 `계약금 수령 / 잔금 / 입주 / 기타` 값은 보존·표시만 함 |
| 이번 단계 내용 | `activity_note` | 긴 텍스트 | 아니오 | 해당 단계의 확인 내용. 주민번호·결제·계약서 파일은 저장하지 않음 |
| 단계 후 계약 상태 | `contract_status_after` | 자동 | 예 | 선택한 단계에서 자동 결정되어 계약 요약과 연결 매물 상태에 반영됨 |
| 생성일시·수정일시 | `created_at`, `updated_at` | 날짜·시간 | 자동 | 시스템이 기록 |

### 계약 기록 규칙

- 302호의 `5월 시작 / 6개월 단기계약`과 `11월 시작 / 3개월 단기계약`은 별도 계약 기록 두 건으로 저장한다.
- 계약을 해지하거나 만료해도 삭제하지 않고 상태만 바꿔 이력을 남긴다.
- 잘못 등록한 계약은 계약 조회·수정에서 확인 후 완전 삭제할 수 있다. 이 경우 매물과 상담 기록은 삭제하지 않는다.
- 계약 완료 상태는 실제 확인 후에만 선택한다.
- 계약 상태를 `계약 진행` 또는 `잔금 예정`으로 바꾸면 연결된 현재 매물은 `계약 진행 중`으로, `계약 완료`로 바꾸면 매물은 `계약 완료`·종료 사유 `계약 완료`·처리일 종료일로 자동 반영한다. `해지` 또는 `만료`는 아직 종료되지 않은 `계약 진행 중` 매물만 `공실`로 되돌린다. 이미 계약 완료로 종료된 매물은 계약 상태를 다시 바꿔도 자동 재오픈하지 않는다.
- 가계약금만 받은 단계에서는 계약 상태를 `계약 진행`으로 두고 계약 진행 시작일만 기록할 수 있다. 정식 계약 뒤 정식 계약일과 임대차 기간을 이어서 입력한다.
- 계약금 전체와 가계약금 수령액을 함께 입력하면 계약금 미수령액은 화면에서 자동 계산한다. 여러 차례의 입금 내역·결제 처리는 관리하지 않는다.
- 계약 진행 시작일·정식 계약일·계약금 추가 수령 예정일·잔금 예정일·임대차 종료일을 계약 일정과 통합 오늘 할 일의 날짜 기준으로 사용한다. 잔금 예정일은 계약 진행 시작일보다 빠를 수 없고, 정식 계약일이 있으면 그보다도 빠를 수 없다.
- 정식계약을 마친 뒤 잔금 예정일은 계약 기본정보에 미래 일정으로 입력한다. 계약 단계 이력의 `잔금 예정`·`계약 완료`는 실제 처리·확인한 날에만 기록하며, 미래 잔금 단계를 미리 이력으로 남기지 않는다.
- 계약 진행·잔금 예정은 출처 상담만 `계약 진행`으로 반영한다. 계약 완료는 다른 진행 중 연결 계약이 없을 때 출처 상담을 `종료 / 계약 완료`로 바꾸고 다음 연락일을 해제한다. 해지·만료는 상담을 자동 재개하지 않는다.
- 기존 계약에 출처 상담을 나중에 연결한 경우에는 사용자가 `현재 계약 상태를 연결 상담에 반영`을 명시적으로 선택했을 때만 현재 상태를 상담에 반영한다.
- 주민번호, 결제, 계약서·신분증 파일은 저장하지 않는다. 계약자 연락처와 계약금·잔금은 계약관리의 내부정보로만 저장한다.
- 계약 조회 결과 엑셀에는 계약자 연락처를 포함하지 않는다. 계약번호·매물번호, 건물·호실, 계약 유형·상태·날짜·기간·금액·계약 메모만 내부 업무용으로 내보낼 수 있다.
- 계약 단계 이력은 계약 조회·수정의 상세 화면에서만 추가·수정·삭제한다. 이력의 최신 처리일과 저장 순서 기준 상태를 계약 요약에 반영하며, 기존 계약의 날짜·금액 필드는 자동으로 바꾸지 않는다.

### 매물 회차별 현재 광고 현황

광고 현황은 아래 기준으로 별도 관리한다. 광고 이력·문구·링크·비용·외부 광고 사이트 연동은 저장하지 않는다.

| 항목 | 저장 이름 | 형식 | 필수 | 규칙 |
|---|---|---|---|---|
| 광고 현황 번호 | `id` | 정수 | 자동 | 내부 번호 |
| 매물 회차 번호 | `listing_id` | 정수 | 예 | 해당 시점의 매물 회차에 연결 |
| 광고 채널 | `advertising_channel` | 선택·짧은 텍스트 | 예 | 당근 / 직방 / 네이버 / 직접입력 |
| 현재 광고 상태 | `advertising_status` | 선택 | 예 | 광고 중 / 광고 중지 / 확인 필요 |
| 마지막 광고 확인일 | `last_checked_date` | 날짜 | 아니오 | 마지막으로 게재 여부를 확인한 날 |
| 생성·수정일시 | `created_at`, `updated_at` | 날짜·시간 | 자동 | 시스템이 기록 |

- 같은 `listing_id + advertising_channel` 조합은 하나만 저장한다. 상태 변경은 새 행을 만들지 않고 기존 행을 수정한다.
- 종료된 매물은 기본 광고 현황 목록에서 제외한다. 광고 현황은 오늘 할 일과 분리해 광고관리 탭에서만 확인한다.

상담 기록은 아래 기준으로 추가한다. 고객 이름과 연락처는 팔로업에 필요한 최소 내부정보로 저장하되, 방문 예약·자동 문자·주민번호 등은 이번 범위에 포함하지 않는다.

# 11-1. 상담 기록

상담 기록은 계약 기록과 별도로 관리한다. `매물 상담`은 해당 매물 회차에 연결하고, `일반 상담`은 매물 없이 저장한 뒤 필요할 때 매물 회차를 연결할 수 있다.

| 화면명 | DB 항목명 | 형식 | 필수 | 설명 / 규칙 |
|---|---|---|---:|---|
| 상담 번호 | `id` | 정수 | 자동 | 상담 기록의 내부 번호. 화면·엑셀에는 `S-000001` 형식으로 표시 |
| 매물 회차 번호 | `listing_id` | 정수 | 아니오 | 매물 상담은 어느 매물에 대한 상담인지 연결한다. 일반 상담은 비워 둘 수 있다. |
| 상담 구분 | `consultation_category` | 선택 | 예 | 매물 상담 / 일반 상담 |
| 고객 이름 | `customer_name` | 짧은 텍스트 | 아니오 | 등록 화면에서 입력하지 않는다. 기존 DB 필수 제약을 위해 새 기록은 `미입력`으로 저장하며, 기본 목록·일반 엑셀에 표시하지 않음 |
| 고객 연락처 | `customer_phone` | 짧은 텍스트 | 아니오 | 전화 또는 휴대전화 번호. 비워도 저장하며 새 기록은 `미입력`으로 저장. 상담관리 조회 목록·상담 상세·내부 팔로업용 상담 엑셀에서만 확인 |
| 상담일 | `consulted_date` | 날짜 | 예 | 실제 상담한 날짜 |
| 상담 종류 | `consultation_type` | 선택 | 예 | 전화 / 문자 / 방문 / 기타 |
| 유입 경로 | `consultation_source` | 선택 | 아니오 | 미입력 / 직방 / 다방 / 당근 / 네이버 / 워크인 / 타부동산 연계. 고객이 상담으로 들어온 경로 |
| 상담 내용 | `consultation_note` | 긴 텍스트 | 아니오 | 업무 진행 내용. 비워도 저장하며 새 기록은 `미입력`으로 저장 |
| 희망 지역 | `desired_area` | 짧은 텍스트 | 아니오 | 일반·매물 상담 고객이 원하는 지역 |
| 희망 방 형태 | `desired_room_type` | 짧은 텍스트 | 아니오 | 일반·매물 상담 고객이 원하는 방 형태 |
| 희망 보증금 | `desired_deposit_manwon` | 정수 | 아니오 | 상담 고객의 희망 보증금. 단위 만원 |
| 희망 월세 | `desired_monthly_rent_manwon` | 정수 | 아니오 | 상담 고객의 희망 월세. 단위 만원 |
| 희망 입주 가능일 | `desired_available_from_date` | 날짜 | 아니오 | 일반·매물 상담 고객이 입주할 수 있는 희망 날짜. 모르면 비워 둔다. |
| 다음 연락일 | `next_contact_date` | 날짜 | 아니오 | 다음 연락이 필요할 때만 입력 |
| 상담 상태 | `consultation_status` | 선택 | 예 | 진행 중 / 보류 / 종료 / 확인 필요 |
| 생성일시·수정일시 | `created_at`, `updated_at` | 날짜·시간 | 자동 | 시스템이 기록 |

### 상담 기록 규칙

- 상담이 계약으로 이어져도 상담 기록을 계약 기록으로 바꾸거나 삭제하지 않는다.
- 일반 상담은 매물 없이 저장할 수 있고, 맞는 매물이 정해진 뒤 상담 상세에서 해당 매물 회차를 연결할 수 있다.
- 잘못 등록한 상담은 상담 조회·수정에서 확인 후 완전 삭제할 수 있다. 이 경우 매물과 계약 기록은 삭제하지 않는다.
- 고객 이름은 상담 상세에서만 확인하고, 기본 매물 목록·일반 엑셀·외부 공유에 포함하지 않는다. 고객 연락처는 상담관리 조회 목록과 내부 팔로업용 상담 엑셀에서만 확인하며, 기본 매물 목록·오늘 할 일·외부 공유에는 포함하지 않는다.
- 상담 조회 결과 엑셀에는 상담 번호·연결 매물번호와 고객 연락처를 내부 팔로업용으로 포함한다. 고객 이름과 자유 입력 상담 내용은 제외하며, 이 파일은 외부 공유·개인 기기 보관을 금지한다.
- 주민번호, 신분증, 계좌번호 등 민감 개인정보는 저장하지 않는다.
- 자동 문자 발송, 방문 예약 달력, 고객별 통합 CRM은 이번 범위에 넣지 않는다.
- 상담 상태가 `확인 필요`이면 상담관리 목록의 해야 할 일에 `상담 확인 필요`로 표시한다.
- 다음 연락일이 오늘이거나 지나고 상담이 종료되지 않았으면 상담관리 목록의 해야 할 일에 `다음 연락 필요`로 표시한다.
- 다음 연락일이 더 이상 필요 없으면 상담 상세·수정의 `다음 연락일 지정 취소`를 선택해 빈값으로 저장한다.
- 상담 조회에서는 상담 구분, 상담 상태, 상담일 시작·종료일, 다음 연락 필요 조건을 함께 적용할 수 있다. 상담일 종료일은 시작일보다 빠를 수 없다.

# 12. 구현 전 확정이 필요한 항목

아래는 실제 사례를 보고 확정한다. 개발 중 임의로 결정하지 않는다.

1. `룸 형태` 목록에 주인세대·상가주택을 기본값으로 넣을지 여부
2. `주차`를 가능/제한적 정도로 둘지, 주차 대수·자주식 여부까지 관리할지 여부
3. 관리비 포함 항목을 체크박스로 세분화할 시점
4. 단기계약 가격을 별도 숫자 항목으로 둘지, 우선 메모로 둘지 여부
5. 광고 상태를 1차 기본 목록에 넣을지 여부
6. `확인완료`로 판단하는 최소 정보 기준
7. 사진 보유 여부를 `있음 / 없음 / 확인 필요`로 판단하는 사무실 기준

## 12-1. 오늘 할 일 완료 체크

오늘 할 일은 원본 매물·계약·상담 기록에서 다시 계산한다. 업무를 체크해도 원본 일정·상태를 자동으로 바꾸지 않으며, 같은 업무번호·업무 종류·기한 조합의 완료 상태만 별도로 저장한다.

| 화면명 | DB 항목명 | 형식 | 필수 | 설명 / 규칙 |
|---|---|---|---:|---|
| 업무 식별키 | `task_key` | 짧은 텍스트 | 예 | 업무 구분·원본 기록 번호·업무 종류·기한으로 만든 내부 키. 화면에 직접 표시하지 않음 |
| 완료 시각 | `completed_at` | 날짜·시간 | 자동 | 체크한 시각. 체크 해제하면 완료 기록을 삭제 |
| 수정 시각 | `updated_at` | 날짜·시간 | 자동 | 완료 체크 상태를 마지막으로 바꾼 시각 |

- 원본 기한이나 업무 종류가 바뀌면 새 업무 식별키로 계산되어 미완료로 표시한다.
- 완료 체크는 날짜가 있는 오늘·지연 업무의 기존 표 마지막 `완료` 열에만 제공한다. 상시 확인 필요는 완료 체크 없이 기존 목록으로 표시한다.
- 완료 체크와 해제는 자동 백업 대상이며, 오늘 할 일 엑셀에는 완료 여부를 포함한다.

## 13. 이 문서의 사용 방법

- 화면을 만들 때: `화면명`과 `입력 방식`을 그대로 사용한다.
- SQLite를 만들 때: `DB 항목명`, `형식`, `필수`를 기준으로 열을 만든다.
- 초기 등록 때: 9장의 원칙에 따라 현재 필요한 매물부터 직접 등록한다.
- 새로운 항목이 필요할 때: 먼저 건물·호실·매물 회차 중 어디에 속하는지 판단한 뒤 추가한다.

이 문서에서 정의하지 않은 항목은 코드에 바로 추가하지 않고, 실제 업무에서 반복적으로 필요한지 먼저 확인한다.
